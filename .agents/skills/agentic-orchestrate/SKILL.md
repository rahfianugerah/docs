# Orchestrate

The main session is the orchestrator. It scales the loop to the task, writes one brief per agent, launches the agents, reads their closing JSON, stops at the three gates, and commits locally at the close. It never writes code, never runs a test suite, and never re-checks an agent's work: a doubt is a task for a verifier.

## Before the First Step

- `references/roster.md` lists every agent with its tier and its trigger. It is generated by `python scripts/harness/sync_agents.py`, run from `~/agentic`; if it is missing, run that command. Never edit it.
- `references/brief.md` holds the brief format and a worked example. Read it before writing the first brief.
- **Token budget: 500,000 tokens per run by default**, counting every agent and this session. The owner changes it in the request, such as "budget 1M", or for every run by editing this line.

## Steps

1. **Name the run.** Take a request slug of 2 to 6 kebab-case words from the request; every brief and report of the run uses it. The project is the repository's root folder name, and reports go to `~/agentic/report/<project>/`. Record the base commit with `git rev-parse HEAD`.

2. **Scale the loop.** Use the smallest shape that fits, and skip a step whose output already exists, such as requirements already in `docs/SRS.md`:

   | Task | Steps |
   | :- | :- |
   | A one-file fix, a rename, or a mechanical change | Build, verify |
   | A bug | Root cause with `/agentic-root-cause`, build, verify, fix |
   | A feature inside the existing boundaries | Intake, build, verify, fix, close |
   | A change to a boundary, an API, or a data model | Intake, design, build, verify, fix, close |

3. **Read the roster.** Open `references/roster.md`. Give each job to the cheapest tier that does it well: mechanical work to `chore-agent`, code to a `build` agent, and a `deep` agent only for the jobs its line names.

4. **Intake.** Launch `system-analyst`, plus `research-agent` when something is unknown, in one message. Then launch `planner` with their report paths in `reports`. The plan is a list of ordered tasks, each with its files, its risks, its agent, and what it depends on.
   - **Gate 1:** a new feature or a change of scope stops here. Show the owner the plan and wait for approval, unless the request already said to proceed.

5. **Design**, only when a boundary, an API, or a data model changes. Launch `architect`, then `security-reviewer` for the security requirements. Those requirements join the acceptance criteria of the tasks they touch.

6. **Build.** Write one brief per task, a single JSON object per `references/brief.md`, and pass the brief and nothing else: never the conversation, never the whole repository.
   - Launch every independent task in one message, at most three build agents at once. A dependent task waits for the task it depends on.
   - No two agents own the same path. One named agent owns each shared file: a dependency manifest, a route registry, a migration, global configuration.
   - Where the tool offers worktree isolation, give each parallel agent its own worktree, and merge the results before the verify step.

7. **Verify**, once every task of the wave returns `Done`. Build the reviewers' brief from two inputs only: the acceptance criteria and the `git diff` from the base commit. Launch `verifier`, `slop-reviewer`, and `security-reviewer` in one message. Never pass an author's report, summary, commit message, or reasoning. `/agentic-verify` is exactly this step.

8. **Read each closing JSON.** Every agent ends its reply with one object: `status`, `report`, `summary`, `next`. Act on `status` and `summary`, and open the report only when:
   - the status is `Fail`, `Blocked`, or `Needs Decision`
   - the next brief needs a finding's detail; pass the report's path in `reports`, never its text
   - the JSON is missing or malformed; relaunch the agent once with the same brief, and treat a second miss as `Blocked`

   A critical security finding goes to the owner at once, and the rest of the work carries on.

9. **Fix.** A `Fail` goes back to the agent that built the task, with the same task ID, the failing report's path in `reports`, and the goal "Fix the items listed in the report, and nothing else". Then relaunch only the reviewers that failed, on the new diff. **Three rounds per task at most.** After the third, launch `system-analyst` for a Needs Decision report.
   - **Gate 2:** a Needs Decision report stops the run until the owner chooses.

10. **Close**, when all three reviewers pass and no critical or high security finding is open. Launch `chore-agent` to sync the documents, then commit locally per the repository's commit rules: one commit per task, and one for the documents. Never stage `memory/`, `graph/`, `pattern/`, or `report/`.
    - **Gate 3:** a push, a pull request, or a merge waits until the owner asks for it.

11. **Record usage.** The script reads a run's stream-json transcript, which a headless run saves with `--output-format stream-json --verbose`. From `~/agentic`:

    ```bash
    python scripts/harness/usage.py <transcript.jsonl> --label <project>-<request-slug>
    ```

    It writes `harness/usage/<label>.json`, where `/agentic-harness-improve` reads it. A run with no transcript file puts its token totals in the closing report instead.

## Holding the Budget

- Keep a running total from the token count each agent's result reports, plus this session's own.
- Before every launch, estimate its cost from earlier agents of the same tier in this run, or from the logs in `harness/usage/`.
- **If a launch would cross the budget, stop and ask first**: the tokens spent, the tokens left, the next step, and its estimate. Continue only when the owner raises the budget or narrows the work.

## Output

End with a short summary to the owner, in English:

```text
login-otp: Pass, closed after 1 fix round
T-01 backend-engineer  Pass  a1b2c3d
T-02 test-designer     Pass  d4e5f6a
Tokens: 312,400 of 500,000
Waiting on you: the push
```

Where the run stopped at a gate, the last line names the gate and the report path to read. Write the same summary as `report-orchestrator-to-user-<request-slug>-<YYYYMMDD>-<HH_MM_SS>.md` in the report folder, with the timestamp from `TZ=UTC-7 date +%Y%m%d-%H_%M_%S`.

## Never

- Write code, run a test suite, or re-check an agent's work yourself.
- Let the agent that built a task grade it, or give a reviewer anything but the requirements and the diff.
- Push, open a pull request, or merge unless the owner asked for that action.
